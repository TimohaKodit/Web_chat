# Правила работы над проектом

## Что это за проект

Учебный веб-мессенджер на FastAPI + WebSocket. Цель — научиться, а не быстро
получить работающий репозиторий. Проект идёт в портфолио на GitHub, в планах —
деплой на реальный сервер.

## Роль Claude в этом проекте — наставник, а не исполнитель

1. **Не писать готовый код проекта и не править файлы за автора.** Направлять:
   объяснять механику, задавать наводящие вопросы, показывать, где ошибка, — но
   решение пишет автор.
2. **Исключение — базовый синтаксис языка.** Автор подзабыл Python и FastAPI,
   поэтому напоминать синтаксис (try/except, списки, словари, классы, async)
   можно и нужно — но **на нейтральных примерах**, не на его задаче.
3. **Исключение — фронтенд.** Автор им не занимается и не изучает его. HTML/JS
   в `app/static/` пишет Claude, когда бэкенд-часть этапа закрыта.
4. **Одна задача за раз.** Не выдавать списками по 3-5 задач — автор просил
   давать ровно одну и писать короче.
5. **Всегда давать ссылки на источники** — официальная документация, MDN, RFC.
6. **Ревью кода — через вопросы.** Не «вот исправленный код», а «посмотри на эту
   строку: что она возвращает?».
7. Если код всё же приводится — только короткий фрагмент, с разбором, что там
   происходит и почему.

## Как ведётся работа

Цикл одной задачи:

```
git switch main && git pull
git switch -c <тип>/<описание>
   ... код, git add, git commit ...
git push -u origin <ветка>
   ... PR на GitHub, читаем диф, мержим, удаляем ветку ...
git switch main && git pull && git branch -d <ветка>
```

Типы веток: `feature/`, `fix/`, `refactor/`, `chore/`, `docs/`.
Сообщения коммитов — в стиле Conventional Commits (`feat:`, `fix:`, `refactor:`).

Правило: **сначала заставь работать, потом сделай красиво** — фича и рефакторинг
идут разными коммитами.

**Важно:** любые правки — только после `git switch main && git pull`. Правка,
сделанная на уже смерженной ветке, теряется или создаёт лишний PR.

## Стек

- Python + FastAPI, uvicorn
- WebSocket для реального времени
- PostgreSQL (впереди)
- Docker + nginx для деплоя (впереди)

## Запуск

```powershell
.\.venv\Scripts\Activate.ps1
uvicorn app.main:app --reload --timeout-graceful-shutdown 3
```

Запускать из корня проекта. `--timeout-graceful-shutdown` нужен, чтобы сервер не
висел на Ctrl+C, ожидая открытые WebSocket-соединения.

Если порт занят зависшим процессом:

```powershell
Get-Process python | Stop-Process -Force
```

## Как отлаживать

«Не работает» — это не диагноз. Диагноз — конкретная строка из логов. Два места:

1. **Консоль uvicorn** — трейсбеки сервера. Читать снизу вверх: последняя строка
   говорит *что* случилось, первая строка с путём `app\...` — *где*.
2. **DevTools (F12)** → Console (ошибки JS) и Network → фильтр WS → Messages
   (кадры в обе стороны). Успешный хендшейк — статус `101`.

Ломать протокол — из консоли браузера, а не через интерфейс: свой фронт всегда
шлёт правильные данные, а реальный клиент может прислать что угодно. Готовые
сценарии — в README, раздел «Ручная проверка».

## Дорожная карта

Как читать пункт: **Зачем** — мотивация; **Изучить** — что понять до кода;
**Реализовать** — что сделать; **Готово, когда** — критерии приёмки;
**Проверка** — как убедиться; **Грабли** — где обычно ломается.

Один пункт = одна ветка = один PR. Отметку `[x]` ставит автор, и только когда
выполнены **все** критерии. Фронт (`app/static/`) пишет Claude после закрытия
бэкенд-части пункта.

- [ ] **8. Валидация через Pydantic**
  - **Зачем.** Ручные `if` по каждому полю не масштабируются. Нужно описать,
    *какими должны быть* данные, и пусть библиотека проверяет сама. Заодно
    появляется единое место, где виден весь протокол.
  - **Изучить.** `BaseModel` — класс-описание данных; поля с аннотациями типов
    вместо `__init__`; `Field(min_length=, max_length=)` для ограничений;
    `Literal["message", "system"]` — поле принимает только перечисленные
    значения; `model_validate(словарь)` — создать объект с проверкой;
    `ValidationError` — что летит при плохих данных; `model_dump()` — обратно
    в словарь.
  - **Реализовать.**
    1. Файл `app/schemas.py` — модели живут отдельно от логики.
    2. Модель входящего представления: поле `user`, строка, 1–32 символа.
    3. Модель входящего сообщения: поле `text`, строка, 1–1000 символов.
    4. Модели исходящих сообщений (`message`, `system`) — с полем `type`.
    5. В эндпоинте вместо `.get()` + `if` — `model_validate`, а рассылать
       результат `model_dump()`.
    6. Ловить `ValidationError` рядом с `JSONDecodeError`.
  - **Готово, когда.** Весь протокол описан моделями в `schemas.py`; невалидное
    сообщение не роняет сервер и не выбивает других клиентов; отправителю
    уходит `{"type": "error", "text": ...}`, и только ему.
  - **Проверка.** Из консоли браузера: пустое имя, имя из 50 символов,
    `{"user": 123}`, `{"foo": "bar"}`, текст на 5000 символов — всё
    отклоняется, остальные клиенты живы.
  - **Грабли.** `pydantic` становится прямой зависимостью — дописать в
    `requirements.txt`, хотя он и так стоит как зависимость FastAPI. Ошибку
    валидации нельзя рассылать всем — это личный ответ отправителю.
  - **Доки.** <https://docs.pydantic.dev/latest/concepts/models/> ,
    <https://docs.pydantic.dev/latest/concepts/fields/>

- [ ] **9. Структура проекта**
  - **Зачем.** `main.py` уже делает три работы: создаёт приложение, хранит
    соединения, обрабатывает сокет. Дальше добавятся БД и авторизация — файл
    станет нечитаемым. Разделять по смыслу, а не по размеру.
  - **Изучить.** `APIRouter` — как собрать эндпоинты в отдельном файле и
    подключить к приложению; зачем нужен `__init__.py`; принцип «модели
    отдельно, логика отдельно, эндпоинты отдельно»; что такое циклический
    импорт и как он возникает.
  - **Реализовать.**
    1. `app/services/connection_manager.py` — класс менеджера.
    2. `app/routers/ws.py` — эндпоинт `/ws` на `APIRouter`.
    3. `app/schemas.py` — модели (есть после пункта 8).
    4. `main.py` — только создание `FastAPI`, подключение роутеров и `GET /`.
  - **Готово, когда.** `main.py` короче 20 строк; чат работает точно как до
    рефакторинга; ни один модуль не импортирует `main`.
  - **Проверка.** Полный прогон чек-листа из README — поведение не изменилось.
  - **Грабли.** Один экземпляр `manager` на всё приложение: если создать его в
    двух местах, клиенты попадут в разные словари и не увидят друг друга.
  - **Доки.** <https://fastapi.tiangolo.com/tutorial/bigger-applications/>

### Часть 2. Хранение

- [ ] **10. Конфигурация через окружение**
  - **Зачем.** Пароль от базы нельзя держать в коде — он утечёт в git. Плюс
    локально и на сервере настройки разные, а код должен быть один.
  - **Изучить.** Переменные окружения; файл `.env` и почему он **не** попадает
    в репозиторий; `.env.example` как шаблон для других; `pydantic-settings` —
    те же модели Pydantic, но читают значения из окружения; принцип
    «конфигурация — в окружении» из 12-factor.
  - **Реализовать.**
    1. `app/config.py` — класс `Settings` с полями `DATABASE_URL`, `SECRET_KEY`.
    2. `.env` локально (уже в `.gitignore`), `.env.example` — в git.
    3. Один общий экземпляр настроек, который импортируют остальные модули.
  - **Готово, когда.** В коде нет ни одной строки с паролем или хостом БД;
    запуск без нужной переменной падает сразу при старте с понятным
    сообщением, а не посреди работы.
  - **Проверка.** Убрать переменную из `.env` → сервер не стартует и говорит,
    чего не хватает.
  - **Грабли.** После создания `.env` проверить `git status` — его не должно
    быть видно. Если попал в коммит, секрет считается утёкшим, значение менять.
  - **Доки.** <https://docs.pydantic.dev/latest/concepts/pydantic_settings/> ,
    <https://12factor.net/ru/config>

- [ ] **11. PostgreSQL в Docker**
  - **Зачем.** Ставить Postgres на Windows руками — боль и невоспроизводимость.
    Контейнер поднимается одной командой и одинаково работает у всех.
  - **Изучить.** Разница между образом и контейнером; `docker compose` и файл
    `compose.yaml`; порт `5432`; переменные окружения образа `postgres`;
    **тома** (volumes) — почему без них данные исчезают при пересоздании
    контейнера; `psql` как консольный клиент.
  - **Реализовать.**
    1. `compose.yaml` с одним сервисом `db` на образе `postgres`.
    2. Логин, пароль, имя базы — из окружения, не хардкодом.
    3. Именованный том для данных.
  - **Готово, когда.** `docker compose up -d db` поднимает базу; данные живут
    после `docker compose down` и повторного `up`; внутри контейнера
    выполняется `SELECT 1`.
  - **Проверка.** Создать таблицу через `psql`, перезапустить контейнер,
    убедиться, что таблица на месте.
  - **Грабли.** Docker Desktop под Windows должен быть запущен. Приложение пока
    не в докере — подключается к базе по `localhost:5432`.
  - **Доки.** <https://hub.docker.com/_/postgres> , <https://docs.docker.com/compose/>

- [ ] **12. SQLAlchemy async + Alembic**
  - **Зачем.** Писать SQL строками — легко получить инъекцию и опечатку без
    подсказок IDE. ORM даёт таблицы как питоновские классы. Миграции — история
    изменений схемы, как git для базы.
  - **Изучить.** Что делает ORM; декларативные модели и `DeclarativeBase`;
    `AsyncSession` и `async_sessionmaker`; почему для async нужен драйвер
    `asyncpg`, а не `psycopg2`; `Depends` для выдачи сессии в эндпоинт; что
    такое миграция, `alembic revision --autogenerate`, `upgrade` / `downgrade`.
  - **Реализовать.**
    1. `app/database.py` — движок, фабрика сессий, зависимость `get_session`.
    2. `app/models.py` — `User` (`id`, `username` уникальный, `created_at`) и
       `Message` (`id`, `user_id` → FK, `text`, `created_at`).
    3. Alembic: инициализация, настройка на async-движок и на `DATABASE_URL`
       из настроек, первая автогенерируемая миграция.
  - **Готово, когда.** `alembic upgrade head` создаёт таблицы;
    `downgrade base` откатывает начисто; сессия попадает в эндпоинты через
    `Depends`, а не создаётся руками в каждом.
  - **Проверка.** `upgrade` → посмотреть таблицы в `psql` → `downgrade` →
    таблиц нет → снова `upgrade`.
  - **Грабли.** Строка подключения для async выглядит как
    `postgresql+asyncpg://...` — с синхронной ORM не заработает. Alembic по
    умолчанию синхронный, его `env.py` нужно править под async. Каждая
    миграция коммитится в git — это часть кода.
  - **Доки.** <https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html> ,
    <https://alembic.sqlalchemy.org/en/latest/tutorial.html>

- [ ] **13. История сообщений**
  - **Зачем.** Сейчас перезагрузил страницу — чат пустой. Мессенджер без
    истории мессенджером не является.
  - **Изучить.** Запись в БД внутри обработчика сокета; чтение последних N
    записей с сортировкой по времени; **пагинация** курсором (`before=<id>`) и
    почему `OFFSET` на больших таблицах плох; индекс по `created_at`.
  - **Реализовать.**
    1. При рассылке сохранять сообщение в таблицу.
    2. При подключении отдавать клиенту последние N сообщений (тип вроде
       `history` в протоколе).
    3. `GET /messages?limit=&before=` — постранично, для догрузки вверх.
    4. Индекс по `created_at`.
  - **Готово, когда.** После перезагрузки страницы видна переписка; эндпоинт
    истории отдаёт страницы и не возвращает дубли на границе страниц.
  - **Проверка.** Написать 30 сообщений, перезагрузить, проверить порядок;
    запросить историю двумя страницами и сравнить.
  - **Грабли.** Порядок сортировки: из базы удобно брать «последние сверху», а
    показывать надо «старые сверху» — разворот где-то нужен. Сохранение не
    должно задерживать рассылку.
  - **Доки.** <https://docs.sqlalchemy.org/en/20/orm/queryguide/select.html>

### Часть 3. Пользователи

- [ ] **14. Регистрация и пароли**
  - **Зачем.** Сейчас любой называется кем угодно. Нужны настоящие аккаунты.
  - **Изучить.** Почему пароль нельзя хранить даже в зашифрованном виде; что
    такое хеш и соль; `bcrypt` / `argon2`; почему хеши не сравнивают обычным
    `==`; коды ответов 201 и 409; почему нельзя возвращать хеш в API.
  - **Реализовать.**
    1. `POST /auth/register` — принимает логин и пароль, сохраняет **хеш**.
    2. Проверка уникальности логина → 409 при повторе.
    3. Модель ответа без пароля и хеша.
  - **Готово, когда.** В базе в колонке пароля хеш, а не текст; повторная
    регистрация даёт 409; пароль не появляется ни в логах, ни в ответе, ни в
    `/docs`.
  - **Проверка.** Зарегистрировать через `/docs`, посмотреть строку в `psql`.
    Зарегистрировать второй раз тем же логином — 409.
  - **Грабли.** Уникальность обеспечивать ограничением в БД, а не только `if` в
    коде — два одновременных запроса обойдут проверку в коде.
  - **Доки.** <https://fastapi.tiangolo.com/tutorial/security/> ,
    <https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html>

- [ ] **15. JWT-авторизация**
  - **Зачем.** После логина клиент должен доказывать, кто он, в каждом
    следующем запросе — и без пароля.
  - **Изучить.** Структура JWT (header.payload.signature) и что **payload
    читается кем угодно** — секретов туда не кладут; подпись `HS256` и роль
    `SECRET_KEY`; поле `exp`; `OAuth2PasswordBearer`; зависимость
    `get_current_user`; почему 401, а не 403.
  - **Реализовать.**
    1. `POST /auth/login` — проверяет пароль, выдаёт access-токен.
    2. Функции создания и проверки токена.
    3. Зависимость `get_current_user` — достаёт пользователя по токену.
    4. `GET /me` — защищённый эндпоинт для проверки.
  - **Готово, когда.** `/me` без токена → 401, с валидным → данные
    пользователя, с истёкшим или подделанным → 401; `SECRET_KEY` берётся из
    настроек.
  - **Проверка.** Логин → скопировать токен → `/me` с ним и без него.
    Испортить один символ в токене → 401. Поставить время жизни 10 секунд,
    подождать → 401.
  - **Грабли.** Токен подписан, но **не зашифрован** — содержимое видно на
    jwt.io. Неверный пароль и несуществующий логин должны давать одинаковый
    ответ, иначе можно перебирать существующие логины.
  - **Доки.** <https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/> ,
    <https://datatracker.ietf.org/doc/html/rfc7519>

- [ ] **16. Авторизация в WebSocket**
  - **Зачем.** Свести пункты 7 и 15: имя в чате должно браться из аккаунта, а
    не из слова клиента.
  - **Изучить.** Почему в браузерном `WebSocket` нельзя выставить заголовок
    `Authorization` и какие из этого выходы (query-параметр или первое
    сообщение); коды закрытия WebSocket, в частности `1008`; где проверять
    токен — до `accept()` или после.
  - **Реализовать.**
    1. Клиент передаёт токен при подключении.
    2. Сервер проверяет токен; невалидный — закрыть с кодом `1008`.
    3. Имя для сообщений брать из `User` в БД; убрать доверие к полю `user`
       от клиента.
    4. Переписать хранение в менеджере: связка `websocket → user_id`.
  - **Готово, когда.** Подключение без токена или с плохим токеном закрывается
    с `1008`; подделать чужое имя из консоли браузера невозможно.
  - **Проверка.** Подключиться без токена, с мусорным токеном, с токеном
    другого пользователя — и попробовать отправить сообщение с чужим `user`
    в теле.
  - **Грабли.** Токен в query-параметре попадает в логи сервера — знать об этом
    ограничении. Фронт и тесты после этого пункта нужно править.
  - **Доки.** <https://developer.mozilla.org/en-US/docs/Web/API/CloseEvent/code>

- [ ] **17. Комнаты**
  - **Зачем.** Один общий чат — это демо. Комнаты превращают его в мессенджер.
  - **Изучить.** Связь many-to-many и таблица-связка; `relationship`;
    параметры пути (`/ws/{room_id}`); как хранить подключения по комнатам —
    словарь словарей или составной ключ; проверка, что пользователь состоит
    в комнате.
  - **Реализовать.**
    1. Модель `Room` и связь с `User`; у `Message` появляется `room_id`.
    2. `POST /rooms`, `GET /rooms`, вход в комнату.
    3. `/ws/{room_id}`; рассылка только участникам этой комнаты.
    4. История — по комнате.
  - **Готово, когда.** Сообщение из комнаты A не видно в комнате B; чужой в
    комнату не подключится; история отдаётся по комнате.
  - **Проверка.** Четыре вкладки: два пользователя в A, два в B. Написать в A —
    в B тихо. Попробовать подключиться к комнате, где не состоишь.
  - **Грабли.** Менеджер соединений усложняется — не забыть удалять пустые
    комнаты из структуры, иначе утечка памяти.
  - **Доки.** <https://docs.sqlalchemy.org/en/20/orm/basic_relationships.html>

### Часть 4. Качество

- [ ] **18. Тесты**
  - **Зачем.** Ручной чек-лист из README после каждой правки не прогонишь.
    Тесты делают это за секунды и ловят то, что забыл проверить.
  - **Изучить.** `pytest`; функции `test_*` и `assert`; **фикстуры** и зачем
    они; `TestClient` и его `websocket_connect`; отдельная тестовая база и
    очистка между тестами; `pytest-asyncio` для async-тестов.
  - **Реализовать.**
    1. Папка `tests/`, фикстуры: приложение, тестовая БД, авторизованный клиент.
    2. Тесты авторизации: регистрация, логин, 401 без токена, 409 на дубль.
    3. Тесты WebSocket: два клиента и доставка сообщения; невалидный JSON не
       выбивает второго; подключение без токена закрывается.
    4. Тест истории: сообщения сохраняются и возвращаются.
  - **Готово, когда.** `pytest` зелёный; тесты не зависят от порядка запуска и
    не оставляют мусор в базе; если сломать код руками — виден красный тест.
  - **Проверка.** Запустить дважды подряд — оба раза зелено. Закомментировать
    проверку токена — тест должен упасть.
  - **Грабли.** Тесты не должны ходить в рабочую базу. Каждый тест начинается с
    чистого состояния, иначе «по одному работает, вместе падает».
  - **Доки.** <https://fastapi.tiangolo.com/advanced/testing-websockets/> ,
    <https://docs.pytest.org/en/stable/how-to/fixtures.html>

- [ ] **19. Логирование и обработка ошибок**
  - **Зачем.** `print` нельзя отключить, отфильтровать по уровню или направить
    в файл. На сервере, где нет консоли перед глазами, логи — единственный
    способ понять, что произошло.
  - **Изучить.** Модуль `logging`; уровни DEBUG/INFO/WARNING/ERROR; логгер на
    модуль (`getLogger(__name__)`); почему нельзя логировать пароли и токены;
    обработчики исключений FastAPI; чем `logger.exception` отличается от
    `logger.error`.
  - **Реализовать.**
    1. Настройка логирования в одном месте, уровень — из настроек.
    2. Заменить все `print` на вызовы логгера.
    3. Логировать подключение и отключение (с пользователем и комнатой),
       ошибки валидации, необработанные исключения.
    4. Общий обработчик, чтобы неожиданная ошибка в сокете не убивала остальных.
  - **Готово, когда.** В коде нет `print`; в логах видно, кто подключился и
    отключился; необработанное исключение у одного клиента не влияет на других.
  - **Проверка.** Искусственно бросить исключение в обработчике — остальные
    клиенты продолжают переписку, в логе есть трейсбек.
  - **Грабли.** Не логировать содержимое сообщений целиком — это переписка
    пользователей.
  - **Доки.** <https://docs.python.org/3/howto/logging.html> ,
    <https://fastapi.tiangolo.com/tutorial/handling-errors/>

- [ ] **20. Линтер и pre-commit**
  - **Зачем.** Съехавшие отступы, неиспользованные импорты, разнобой в кавычках
    — шум в дифах. Пусть инструмент делает это сам.
  - **Изучить.** Разница между линтером (ищет проблемы) и форматтером
    (переписывает стиль); `ruff` как оба сразу; настройка в `pyproject.toml`;
    `pre-commit` — хуки git, которые запускаются до коммита.
  - **Реализовать.**
    1. `ruff` в зависимостях разработки, настройка в `pyproject.toml`.
    2. Один раз прогнать `ruff format .`, исправить замечания `ruff check .`.
    3. `.pre-commit-config.yaml` с хуками ruff, установить хуки.
  - **Готово, когда.** `ruff check .` и `ruff format --check .` чистые; попытка
    закоммитить неформатированный файл останавливается хуком.
  - **Проверка.** Испортить отступы, попробовать закоммитить — хук не пустит.
  - **Грабли.** Форматирование всего проекта разом даст огромный диф — делать
    отдельным коммитом `style:`, не смешивая с логикой.
  - **Доки.** <https://docs.astral.sh/ruff/> , <https://pre-commit.com/>

- [ ] **21. CI на GitHub Actions**
  - **Зачем.** Тесты, которые надо помнить запускать, рано или поздно не
    запускаются. CI гоняет их на каждый PR сам.
  - **Изучить.** Что такое workflow, job, step; триггеры `push` и
    `pull_request`; `services` — как поднять Postgres для тестов; кеширование
    зависимостей; branch protection на GitHub.
  - **Реализовать.**
    1. `.github/workflows/ci.yml`: установка Python, зависимостей, `ruff`,
       `pytest`.
    2. Postgres как service-контейнер для тестов.
    3. В настройках репозитория — запретить мерж при красном CI.
  - **Готово, когда.** На каждом PR видно галочку или крестик; сломанный тест
    блокирует мерж.
  - **Проверка.** Отправить PR с намеренно сломанным тестом — CI красный, мерж
    недоступен.
  - **Грабли.** Секреты не пишутся в yml — только через Secrets репозитория.
    «Локально работает, в CI нет» — обычно из-за отсутствующих переменных.
  - **Доки.** <https://docs.github.com/en/actions/quickstart> ,
    <https://docs.github.com/en/actions/use-cases-and-examples/using-containerized-services/creating-postgresql-service-containers>

### Часть 5. Деплой

- [ ] **22. Dockerfile приложения**
  - **Зачем.** На сервере не будет ни venv, ни нужной версии Python. Образ
    везёт всё с собой.
  - **Изучить.** Слои и почему порядок команд влияет на скорость сборки;
    `.dockerignore`; multi-stage build; запуск от непривилегированного
    пользователя; почему на проде не используют `--reload`; `depends_on` и
    healthcheck.
  - **Реализовать.**
    1. `Dockerfile`: сначала зависимости, потом код — чтобы кеш не ломался.
    2. `.dockerignore` (`.venv`, `.git`, `__pycache__`, `.env`).
    3. В `compose.yaml` добавить сервис `app` рядом с `db`.
    4. Миграции применяются при старте.
  - **Готово, когда.** `docker compose up` поднимает приложение и базу; чат
    работает в контейнере; образ меньше 300 МБ; в образе нет `.env`.
  - **Проверка.** Собрать, поднять, открыть чат. Изменить одну строку кода —
    пересборка должна быть быстрой (кеш зависимостей цел).
  - **Грабли.** Внутри compose база доступна по имени сервиса `db`, а не по
    `localhost` — `DATABASE_URL` для контейнера другой. Секреты в образ не
    вкладывать, передавать окружением.
  - **Доки.** <https://docs.docker.com/get-started/> ,
    <https://fastapi.tiangolo.com/deployment/docker/>

- [ ] **23. nginx + HTTPS**
  - **Зачем.** Держать приложение открытым в интернет напрямую нельзя. Плюс без
    TLS браузеры ограничивают возможности, а трафик читается по пути.
  - **Изучить.** Что делает reverse proxy; **зачем для WebSocket нужны
    заголовки `Upgrade` и `Connection`** — без них соединение молча рвётся, это
    классическая ошибка; `wss://` против `ws://`; Let's Encrypt и certbot;
    редирект с http на https.
  - **Реализовать.**
    1. Сервис `nginx` в compose, конфиг с проксированием на `app`.
    2. Отдельная секция для `/ws` с заголовками апгрейда.
    3. Сертификат Let's Encrypt и автопродление.
    4. Редирект http → https.
  - **Готово, когда.** Сайт открывается по `https://домен`; чат работает через
    `wss://`; http редиректит на https; порт приложения снаружи не доступен.
  - **Проверка.** Открыть чат по домену с телефона. В DevTools убедиться, что
    сокет — `wss` и хендшейк `101`.
  - **Грабли.** Забытые заголовки апгрейда — сокет не поднимается, а логи почти
    пустые. Таймаут nginx по умолчанию рвёт долгие соединения — увеличить.
  - **Доки.** <https://nginx.org/en/docs/http/websocket.html> ,
    <https://certbot.eff.org/>

- [ ] **24. VPS**
  - **Зачем.** Задеплоить и получить публичный адрес — шаг, без которого
    проект не проверить «в реальности».
  - **Изучить.** SSH-ключи вместо пароля; отдельный пользователь вместо root;
    `ufw` и принцип «закрыто всё, кроме нужного»; установка docker на Ubuntu;
    `restart: unless-stopped`; где живёт `.env` на сервере.
  - **Реализовать.**
    1. Сервер, домен, A-запись на IP.
    2. Пользователь без root, вход по ключу, вход по паролю отключён.
    3. `ufw`: открыты только 22, 80, 443.
    4. Docker, репозиторий, `.env`, `docker compose up -d`.
  - **Готово, когда.** Чат доступен по домену; SSH только по ключу; открыты
    только три порта; после `reboot` всё поднимается само.
  - **Проверка.** Перезагрузить сервер и, не заходя на него, открыть чат.
    Попробовать зайти по SSH с паролем — должно отказать.
  - **Грабли.** Отключать пароль в SSH только **после** проверки, что вход по
    ключу работает, — иначе потеряешь доступ. `.env` на сервер копируется
    руками или через secrets, в git его нет.
  - **Доки.** <https://docs.docker.com/engine/install/ubuntu/> ,
    <https://ubuntu.com/server/docs/firewalls>

- [ ] **25. Автодеплой**
  - **Зачем.** Ручной деплой по SSH забывается и делается с ошибками.
  - **Изучить.** Как CI получает доступ к серверу (deploy-ключ в secrets);
    сборка и публикация образа в registry; обновление контейнера на сервере;
    что делать, если новая версия не поднялась.
  - **Реализовать.**
    1. Workflow: пуш в `main` → тесты → сборка образа → публикация.
    2. Доставка на сервер (SSH-action или watchtower) и перезапуск сервиса.
    3. Миграции применяются при деплое.
  - **Готово, когда.** Пуш в `main` без ручных действий обновляет сайт; красный
    CI деплой не запускает.
  - **Проверка.** Изменить заголовок страницы, запушить, дождаться и обновить
    сайт в браузере.
  - **Грабли.** Ключи и пароли — только в GitHub Secrets. Деплой запускать
    после тестов, а не параллельно с ними.
  - **Доки.** <https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions>
